# Опис маршрутів та інтерфейсів

Нижче наведено основні вебмаршрути Request Portal. Маршрути, що працюють із персональними або службовими даними, потребують автентифікації та перевірки ролі.

| HTTP-метод | URL-маршрут | Призначення | Роль, яка має доступ |
|---|---|---|---|
| **GET** | `/` | Перегляд каталогу активних послуг | Усі відвідувачі |
| **GET** | `/up` | Перевірка доступності вебзастосунку | Усі відвідувачі |
| **GET** | `/my/requests` | Перегляд списку власних звернень клієнта | Клієнт |
| **POST** | `/my/requests` | Створення нового звернення | Клієнт |
| **POST** | `/my/requests/{id}/cancel` | Скасування власного звернення | Клієнт; лише для статусу **Нова** |
| **GET** | `/manager/requests` | Перегляд усіх звернень і застосування фільтрів | Менеджер |
| **POST** | `/manager/requests/{id}/assign` | Призначення поточного менеджера відповідальним за звернення | Менеджер |
| **PATCH** | `/manager/requests/{id}/status` | Зміна статусу звернення | Менеджер |

## Додаткові правила інтерфейсу

- `{id}` — ідентифікатор звернення.
- Маршрути клієнта `/my/requests` доступні лише автентифікованим клієнтам.
- Маршрути `/manager/requests` доступні лише автентифікованим користувачам із роллю **Менеджер**.
- Для переходу до статусу **Відхилена** у запиті `PATCH` потрібно передати поле `rejection_reason`.
- Дозволені переходи статусів: **Нова → В роботі → Завершена**; на етапах **Нова** та **В роботі** також можливий перехід до **Відхилена**.

## Перевірка доступності та навантаження

Маршрут `GET /up` є health-check Laravel: він підтверджує, що застосунок обробляє запит, і в штатному стані повертає HTTP 200 та сторінку з текстом `Application up`. Сам по собі цей маршрут не перевіряє з'єднання з БД; для цього в навантажувальному прогоні також використовується `GET /services`. Автоматична перевірка:

```bash
php artisan test tests/Feature/AvailabilityTest.php
```

Для локального навантажувального вимірювання потрібні PHP, Composer і Python 3. Скрипти не потребують сторонніх Python-пакетів. Щоб не торкатися робочої бази, створіть окрему SQLite-базу:

```bash
rm -f /tmp/request-portal-benchmark.sqlite
touch /tmp/request-portal-benchmark.sqlite
DB_CONNECTION=sqlite DB_DATABASE=/tmp/request-portal-benchmark.sqlite php artisan migrate --force
python3 scripts/seed-load-test-data.py /tmp/request-portal-benchmark.sqlite
```

Seeder [seed-load-test-data.py](../scripts/seed-load-test-data.py) додає 50 активних послуг лише до порожньої таблиці `services` і завершується помилкою, якщо таблиця вже має записи. Команду `rm` використовуйте лише для цього окремого тимчасового файлу, не для робочої бази. Запустіть сервер у першому терміналі:

```bash
PHP_CLI_SERVER_WORKERS=4 DB_CONNECTION=sqlite DB_DATABASE=/tmp/request-portal-benchmark.sqlite \
  php artisan serve --host 127.0.0.1 --port 8000
```

Після одного контрольного запиту до кожного маршруту запустіть по 200 запитів із 10 одночасними робочими потоками:

```bash
python3 scripts/load-test.py --url http://127.0.0.1:8000/up --requests 200 --concurrency 10
python3 scripts/load-test.py --url http://127.0.0.1:8000/services --requests 200 --concurrency 10
```

Скрипт [load-test.py](../scripts/load-test.py) вимірює повний час HTTP-запиту на клієнті — від початку запиту до читання всього тіла відповіді. Відповідь вважається успішною, якщо її HTTP-статус належить до діапазону 2xx. Звіт містить частку успішних відповідей, пропускну здатність `N / загальний час` і перцентилі затримки. Для p50 та p95 використано метод найближчого рангу: `p = sorted_latencies[ceil(N × percentile) - 1]`. Критерій приймання: усі відповіді успішні та p95 не перевищує 1000 мс.

Результати контрольного вимірювання для демонстраційного релізу v1.0.1 (25.11.2026; PHP 8.2.36, Laravel 12.72.0, SQLite, 50 активних послуг, чотири серверні робочі процеси):

| Маршрут | Запитів | Успішні | p50, мс | p95, мс | Максимум, мс | Запитів/с |
|---|---:|---:|---:|---:|---:|---:|
| `/up` | 200 | 200 (100%) | 61,55 | 107,16 | 188,50 | 135,50 |
| `/services` | 200 | 200 (100%) | 192,04 | 223,91 | 322,58 | 49,42 |

Результат `100%` у цьому короткому прогоні означає лише `200/200` успішних запитів, а не гарантію цілодобової доступності. Вимірювання на SQLite та локальному сервері призначене для демонстрації й порівняння; воно не є SLA або оцінкою production-середовища. Апаратні характеристики машини під час цього вимірювання не фіксувалися.
